# CLAUDE.md — Deckle

## Identity and goals

Deckle is a local Windows utility. The first delivered subsystem is hotkey-triggered voice transcription with the result placed in the clipboard and optional LLM rewriting via Ollama. Other subsystems are added to the same app — ambient lighting driven by screen capture (workstream in progress), future assistance modules (AskHud, AskOllama). The app is a single entry point that gathers several complementary capabilities, not a single-purpose tool.

Two foundational goals guide every decision. **Learning to develop** — understanding what we build takes precedence over the fact that it works; a solution that works without being understood is not a success. **Emancipation from paid services** — local system, autonomous, with no structural cloud dependency. Any proposal that drifts from these two axes must justify it explicitly.

The quality target is a Windows app at Microsoft first-party level. The daily sensory reference is the Windows 11 Settings app, Explorer, and PowerToys. Every UI or platform choice passes the test « est-ce que Microsoft ferait comme ça dans une app Windows Store officielle ? ». If the answer is no, it's the wrong choice, start over.

## Non-negotiable rules

Claude runs Deckle builds locally to validate that the code compiles. The build runs through `dotnet build` (see [src/Deckle.App/CLAUDE.md](src/Deckle.App/CLAUDE.md)), and `scripts/lib/build-run.ps1` remains the daily orchestrator — Claude invokes it from the repo or worktree root. The `publish` remains the maintainer's act; Claude never triggers it. Detailed workflow doctrine lives in the `deckle-workflow` skill.

The commit ships under the sole identity of the maintainer. The `Co-Authored-By: Claude …` trailers and `🤖 Generated with [Claude Code]` lines are excluded — they register Claude as a GitHub contributor, which is false.

## Cross-project doctrine

Before writing or modifying non-trivial code, the following questions are verbalized in the response for those relevant to the request. The doctrine is not an administrative checklist — it's a thinking discipline that forces consideration of what already exists before writing.

**Native primitives first.** Which Windows primitive, which control, which theme resource, which canonical pattern covers the need — including for cases that seem simple. The reinvention signals to detect are concrete indicators that the doctrine was not applied: manual border where a Card theme resource exists, hand-drawn shadow instead of DWM Shell, numeric radius instead of `OverlayCornerRadius` or `ControlCornerRadius`, `MicaBackdrop` on a transient window instead of `DesktopAcrylicBackdrop`, custom caption buttons instead of the native `Microsoft.UI.Xaml.Controls.TitleBar`.

**Zero magic values in XAML.** No `#xxxxxx`, no numeric `CornerRadius="7"`, no arbitrary `BorderThickness`, no hand-computed `BoxShadow`. Everything goes through native Windows theme resources that automatically follow light, dark, contrast and accent: `LayerFillColorDefaultBrush`, `CardBackgroundFillColorDefaultBrush`, `CardStrokeColorDefaultBrush`, `OverlayCornerRadius`, `ControlCornerRadius`, `SystemFillColor*`, `TextFillColor*`. A Figma value without an equivalent theme resource signals the wrong primitive — that's the moment to go back to the spec and find the right control.

**System-managed materials and shadows.** `MicaBackdrop` on long-lived app windows, `DesktopAcrylicBackdrop` on transients (popups, menus, dialogs, HUD, notifications). DWM applies the corresponding rendering, including the Shell shadow on transients. Shadows and rounded corners are DWM's responsibility, not XAML's.

**Named hat.** Architecture, UX, platform: these are not the same postures. Naming the hat at the start of the response frames the thinking mode and invokes the right skills. Engineer for questions of architecture, patterns, threading, performance, tests. WinUI 3 expert for XAML, controls, backdrop, theme resources, lifetime, DWM shadows. Designer for layout, hierarchy, rendering, visual consistency. Product manager for the what, in what order, for whom. A request can require several hats simultaneously — name them all and address the topic from each angle before converging.

## Development environment

The current development environment is Windows 11 on PowerShell, .NET 10 only (no .NET 9 installed), Visual Studio 2026 Community for the build (workload *WinUI application development*), VSCodium with the Claude Code extension for editing. The C++ compiler used for occasional recompilation of the native runtimes is GCC 15.2.0 via MinGW (Scoop), with CMake 4.3.1 and Ninja 1.13.2. Vulkan SDK 1.4.341.1 (Scoop) is required for the GPU backends of the native runtimes (environment variable `VULKAN_SDK` defined). The Windows App SDK reference aligned across the entire solution is `1.8.260317003` (official stable).

### Historical note — `XamlCompiler.exe` MSB3073 bug

Historically (April to May 2026), `dotnet build` crashed without exploitable log with `MSB3073 ... XamlCompiler.exe exited with code 1` on any project that transitively pulls `Microsoft.WindowsAppSDK`. Cause identified in `Microsoft.UI.Xaml.Markup.Compiler.interop.targets`: a condition forces `UseXamlCompilerExecutable=true` as soon as `MSBuildRuntimeType=Core`, which invokes the `net472` EXE instead of the in-process `net6.0` Task. Workaround adopted at the time: build via the Framework `MSBuild.exe` from Visual Studio 2026. Upstream ticket [microsoft-ui-xaml#8871](https://github.com/microsoft/microsoft-ui-xaml/issues/8871) still OPEN with no milestone, a sign that the bug still exists in certain environment combinations.

Since May 24, 2026 (.NET SDK 10.0.204 + `Microsoft.WindowsAppSDK 1.8.260317003`), the bug **no longer reproduces** on this machine. The switch to `dotnet build` and `dotnet test` is recorded by [ADR-0012](docs/adr/0012-adoption-de-dotnet-build-et-dotnet-test.md). If the bug reappears (signal: `MSB3073` at build or test time, log enriched by the WindowsAppSDK 1.8.8 fix that makes the error readable), reintroduce the MSBuild VS workaround — the technical recipe is recorded in the ADR and remains applicable. For future diagnosis of MSBuild problems, `MSBuild ... -bl:fresh.binlog` then `binlogtool search fresh.binlog <pattern>` (installation via `dotnet tool install -g binlogtool`).

## Repository structure

The repo root follows this organization. All application code lives under `src/`, organized into `Deckle.*` modules (one csproj per module, acyclic dependencies, hierarchical sub-namespaces when internal separation justifies it). Canonical technical doctrine references live under `docs/` at the root — all read on demand, not loaded in context by default. Build and publish orchestration scripts live under `scripts/`. The Python benchmark suite lives under `benchmark/` (will be extracted into its own repo later).

Current modules, in dependency-graph order (leaves first). `Deckle.Core` hosts the foundations with no application dependency (`AppPaths`, `JsonSettingsStore<T>`, `CorpusPaths`, Win32 interop). `Deckle.Diagnostics` is the EventSource observability hub (interfaces `ILogWindowSink`/`IHudFeedbackSink`, base class `DeckleEventSource`, `EventEntry`, `LogWindowEventListener`/`JsonlEventListener`/`HudFeedbackEventListener`). `Deckle.Diagnostics.Logging` carries the live journal settings (`LoggingSettings`, `LoggingSettingsService`, `AmbientCaptureGate`). `Deckle.Diagnostics.Telemetry` configures the JSONL listeners and their user gates (`TelemetrySettings`, `TelemetrySettingsService`, `TelemetryListenerBootstrap`). `Deckle.Catalog` is the repository of UI resources named by semantic key — `Loc.cs` (WinAppSDK ResourceLoader facade for `x:Uid`) for localized strings, `Themes/Icons.xaml` + `Glyphs.cs` for the Segoe Fluent Icons glyphs consumed in XAML via `{StaticResource Icon.X}` and in code-behind via `Glyphs.X`. `Deckle.Chrono` is a pure timer with no UI. `Deckle.Audio` covers audio capture (microphone, RMS calibration, mic telemetry) — open to future audio capabilities (TTS, loopback monitoring). `Deckle.Composition` hosts the shared Direct2D and Composition primitives (`ColorSpace`, easing, animators). `Deckle.Vision` (scaffolding in progress) covers screen capture (`Windows.Graphics.Capture`) and image analysis. `Deckle.Lighting` (scaffolding in progress) hosts the LED drivers and the `ILightOutput` abstraction. `Deckle.Hud` gathers the application HUD — `HudWindow`, `HudOverlayWindow`, `HudOverlayManager`, the `HudChrono` UserControl and its `HudState` enum. `Deckle.Shell` covers the system shell (tray, hotkeys, autostart, message-only host). `Deckle.Settings` is the Settings UI shell and the per-module persistence. `Deckle.Llm` is the low-level Ollama HTTP client (administration of installed models, health-check) — reusable by any LLM consumer. `Deckle.Llm.Rewrite` is the rewrite consumer proper: rewrite engine (`LlmService` on `/api/generate` in raw mode), POCO settings and UI (`LlmPage` + sections), prompt templates per model family. `Deckle.Transcription` is the backend-agnostic transcription orchestrator: it carries the state machine, the capture/LLM/paste coordination, the `IAsrBackend` contract, the settings and the UI. `Deckle.Transcription.Whisper` is the child that implements `IAsrBackend` via whisper.cpp (P/Invoke, structs, provisioning catalogs). The parent/children pattern is recorded in [ADR-0010](docs/adr/0010-backend-asr-pluggable-via-iasrbackend.md); a future `Deckle.Transcription.Voxtral` will plug in the same way. `Deckle.Setup` hosts the first-run wizard (downloading natives and models, orchestrates the setup primitives of `Deckle.Transcription.Whisper`). `Deckle.Lighting.Ambient` (scaffolding in progress) is the gaming consumer of `Vision + Lighting`. The host app `Deckle.App` gathers all these modules and provides the WinUI 3 entry point.

Every module that carries non-obvious doctrine exposes its own internal `CLAUDE.md` — to read before touching the module. Today these files exist for `src/Deckle.App/` (host app, LogWindow, lifetime, transverse WinUI 3 pitfalls), `src/Deckle.Audio/` (mic capture), `src/Deckle.Catalog/` (localization + Segoe Fluent glyphs), `src/Deckle.Diagnostics/` + `src/Deckle.Diagnostics.Logging/` + `src/Deckle.Diagnostics.Telemetry/` (EventSource observability, measurement vocabulary, Verbose/Info doctrine), `src/Deckle.Hud/` (HudWindow and UserControls, composite shadows, hybrid bleed, proximity fade), `src/Deckle.Lighting/` (Hue driver + color science pipeline), `src/Deckle.Playground/`, `src/Deckle.Settings/` (Settings architecture + per-module persistence + SettingsHost), `src/Deckle.Setup/` (first-run wizard + provisioning primitives), `src/Deckle.Shell/` (message-only host, hotkeys, tray, autostart), `src/Deckle.Transcription/` (backend-agnostic orchestrator + UIA paste), `src/Deckle.Transcription.Whisper/` (`IAsrBackend` whisper.cpp implementation + native provisioning).

The repo does not contain `whisper.cpp/`: the upstream source is cloned outside (dev workspace, typically `<scoop-root>/persist/whisper.cpp/` or `D:\workspace\whisper.cpp\`) when we want to recompile the native DLLs — the recompilation recipe lives in [docs/reference/reference--native-runtime--1.0.md](docs/reference/reference--native-runtime--1.0.md). The repo also does not contain `native/` nor `models/`: everything lives in `%LOCALAPPDATA%\Deckle\` on the runtime side. The first-run wizard auto-downloads the native bundle from the `native-vX.Y.Z` release of the Deckle repo, and the Whisper models from HuggingFace.

## Reference sheets under `docs/`

The project's writing lives in two regimes. The **timeless doctrine** (internal conventions, pitfalls, anti-patterns, module spec) lives in the `CLAUDE.md` at the root of each concerned module — updated continuously, read on demand when touching the module. The **immutable decided choices** live as ADRs under `docs/adr/` — each captures context, alternatives, decision and consequences, and stays frozen once merged (a revised decision creates a new ADR that supersedes). The **stable versioned specs** transverse or inter-module will live under `docs/reference/` — versioned in the filename, updated by substantial revision. None exist to date; the regime is documented for when a durable transverse spec emerges. The dated **research notes** live under `docs/research/`, artifacts we consult but never treat as sources of truth.

ADRs under `docs/adr/` to date: `0001-record-architecture-decisions.md` (retroactive adoption of the format), `0002-reporter-msix-rester-unpackaged.md`, `0003-distribution-source-only-pour-l-app.md`, `0004-lazy-windows-pour-stabilite-au-boot.md`, `0005-adoption-eventsource-pour-l-observabilite.md`, `0006-structure-diagnostics-parent-logging-telemetry-enfants.md`, `0007-rester-sur-whisper-cpp-surveiller-voxtral.md`, `0008-rester-sur-vulkan-pour-backends-gpu-natifs.md`, `0009-assets-resolus-via-userdataroot.md`, `0010-backend-asr-pluggable-via-iasrbackend.md`, `0011-corpus-normalise-comme-dataset-ml.md`, `0012-adoption-de-dotnet-build-et-dotnet-test.md`, `0013-format-canonique-des-artefacts-agents.md`, `0014-poc-evaluation-voxtral.md`.
