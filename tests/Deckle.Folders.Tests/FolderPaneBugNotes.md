# Folder pane bug notes

## The pane of added folders refuses to open after its items were built again

- **Trigger:** The pane's items built again (`Nav.MenuItems.Clear()` then one new `NavigationViewItem` per added folder, which every folder added, removed, marked as missing or given an icon did), a garbage collection within moments of it, then `NavigationView.IsPaneOpen` set to true. Present since the pane first built its items that way; met on 2026-11-15 when `scripts/deploy-prod.ps1` failed on v0.132.0, whose walk builds the pane about twelve times in a row before it opens it. Intermittent as met: the same Release build passed the full walk on the next run and Deckle Folders walk seven times in a row. Reproduced at will in the walk: build the items again, wait 60 ms, `GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();`, open the pane: 15 openings out of 15 threw.
- **Observed symptom:** `COMException: Unspecified error` (`0x80004005`, E_FAIL) out of the `IsPaneOpen` setter. In the self-check, `folders/folder-icons-pane-open: did not load (navigation did not complete in 3 ms)` and the run stopped on the exception. In the app the exception is survived (`App.UnhandledException` marks it handled): the pane button does nothing.
- **Cause:** Established by experiment that the collection of the items taken out of `MenuItems` is what breaks the pane: with the same sequence, 0 throws out of 30 without building the items again, 0 out of 30 without the forced collection, and 0 out of 30 when the window kept a reference to every item it had taken out. Inferred from the public source of `NavigationViewItem` (`PrepNavigationViewItem`), not observed: each item registers on the pane's `SplitView` for `IsPaneOpen` changes and unregisters only when it is destroyed, so the change still reaches an item the collector has taken apart. A collection that came long after the items were taken out (about 600 ms) did not break the pane; why was not looked into. The first explanation written in the code, a pointer or size handler on each item, was wrong: the failure it was drawn from was this one, passing or failing with the collector's timing.
- **Violated invariant:** A `NavigationViewItem` that was in the pane is never let go while the window lives; commented at `_spareItems` in `src/Deckle.Folders.Views/FoldersWindow.Folders.cs`. `SyncFolderItems` updates the items in place and keeps the item of a removed folder for the next folder added.
- **Recurrence cue:** a self-check that fails on a state that opens a `NavigationView` pane, on some runs only, with `COMException: Unspecified error` after a few milliseconds; a pane button that does nothing once in a while after folders were added or removed; any `MenuItems.Clear()` on a `NavigationView` of a loaded window. The Mail window carries a note of the same exception after its rail is built again (`src/Deckle.Mail.Hub/Views/MailWindow.Capture.cs`); whether it is this cause was not checked.
- **Regression coverage:** no unit test, since a XAML window cannot be built in a unit suite. The self-check walk forces a collection before it opens the pane, in `folders/folder-icons-pane-open` (an added folder added again, which built every item again before the fix) and in `folders/folders-removed-current` (a folder just removed). The first sequence is the one that threw 15 times out of 15 before the fix; the second was not run against the code before the fix.
