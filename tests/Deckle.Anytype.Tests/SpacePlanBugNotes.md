# Space plan bug notes

## A plan stopped at its first write on a space the bot only edits

- **Trigger:** A person creates an empty space in the Anytype app and admits Deckle's bot. The bot joins as an editor, not as the owner. Then a plan that renames native properties or types is applied to that space. The Project management plan renames the native `due_date`, `status`, `project` and `task`.
- **Observed symptom:** `space_plan_apply` failed at its very first write with 403 « failed to update property », and nothing of the plan was written. Observed on « PM trial 2026-11-15 » on 2026-11-15. The same plans built fully on 2026-11-14, on spaces the bot had created itself.
- **Cause:** Anytype refuses an editor's rename of a native property in a space another member created. Creating a property there passes: one `create_property` alone, applied on the same space and with the same key right after, was written. The exact rule behind it is inferred, not read in Anytype's code. It is probably that an editor may not change schema objects it did not create. That matches the 403s already met on collections, queries and views of native types (`docs/anytype-space-plan-coverage.md`). Which other edits of natives it covers (panels, views, display of `project` and `task`) had not been measured when the fix landed. The schema stage treated every write failure as fatal, so the first refusal stopped the run.
- **Violated invariant:** A refusal of one edit blocks none of the other writes. An edit of something the space already held is said as refused and the run goes on. Only a refused creation, or another failure, stops the run. The rule and the trap live in `src/Deckle.Anytype/Plan/EditRefusal.cs` and `SpacePlanExecutor.EditKinds`.
- **Recurrence cue:** A new write in `SchemaAdminGestures.WriteAsync` or `SpacePlanExecutor` that modifies an existing object without going through `EditRefusal`. Or an apply that dies on a 403 before the plan's creations have run.
- **Regression coverage:** In `SchemaAdminGesturesTests`, `ApplyGoesOnWhenTheServerRefusesToRenameANativeProperty` and `ApplyStillCreatesWhatComesAfterARefusedTypeRename` cover this bug. `ApplyStopsWhenTheServerRefusesACreation` keeps the fatal side. `EditRefusalTests` pins the 403-only filter for both clients and checks that no creation is an edit kind. No test runs the structure executor against a server, so its edit kinds are covered only through `EditRefusal`.
