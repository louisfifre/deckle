# Window shortcut bug notes

## A stray "F5" tooltip opens under the Atelier window

- **Trigger:** Keyboard focus landing anywhere inside the Atelier window's root grid, from the window's first release to v0.117.0. Seen through the self-check on 2026-11-11: from about 20:05 every run failed, on builds that had passed minutes before. Reproduced once by sending one key press (F15, bound to nothing) to the desktop before a run, and not reproduced after a mouse move; so the machine's last input being a key is the likely natural trigger, observed on one run only. Reproduced at will by calling `Focus(FocusState.Keyboard)` on the element that already held the focus (the `TitleBar`).
- **Observed symptom:** A 41 x 41 px top-level window (class `Microsoft.UI.Content.PopupWindowSiteBridge`, title `Pop-upHost`) owned by the Atelier window, just under its bottom edge. In the self-check, whose windows stand left of every monitor, WinUI brought the popup back onto the primary monitor at `28,805,69,846`, and the guard of `scripts/self-check.ps1` failed the run: "a self-check window (28,805,69,846) touched the monitor". Read from inside the process, the popup's child was a `ToolTip` of 33 x 32 DIP whose content was the text `F5`; the forced run opened it at the same rectangle, to the pixel.
- **Cause:** Established for the tooltip, inferred for what turns it on. The root `Grid` carried the window's `KeyboardAccelerators` (F5 first). WinUI gives an element that carries accelerators a tooltip naming the first one (`KeyboardAcceleratorPlacementMode`, `Auto` by default) and opens it when a focus change with `FocusState.Keyboard` happens inside the element. Inferred, not read in WinUI's source: a programmatic focus change takes the keyboard state when the last input the system saw was a key, which is how a window that never receives input got there. Why WinUI moves the popup of an off-screen owner onto a monitor was not looked into.
- **Violated invariant:** A layout container that carries a window's shortcuts shows no tooltip of its own; the trap is commented at the root grid of `src/Deckle.Atelier.Views/AtelierWindow.xaml`. The Mail window already set the mode to `Hidden`; the Settings window did not and now does, by the same reasoning, without its tooltip having been seen.
- **Recurrence cue:** a self-check that fails on the "seen or focused" guard with a small rectangle, the same on every run, while its report shows `popups_closed: 1` on one surface; a tooltip showing only a key name under or beside a window; a self-check that passes or fails with what the person last touched, keyboard or mouse.
- **Regression coverage:** `WindowShortcutTooltipTests.AContainerThatCarriesShortcutsShowsNoTooltipForThem` reads the Atelier's markup, since a XAML window cannot be built in a unit suite. It does not cover accelerators added in code, nor the other windows. The self-check's guard remains the check on the running app, but only when the run happens to get the keyboard focus state.
