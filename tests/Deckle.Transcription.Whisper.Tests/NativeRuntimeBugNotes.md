# Native runtime bug notes

## The bundle loaded only where the build machine's PATH reached

- **Trigger:** First run of Deckle on a machine that never had the MinGW toolchain installed, with native bundle 1.9.1 downloaded by the first-run wizard into `%LOCALAPPDATA%\Deckle\native`.
- **Observed symptom:** The first outside tester reported that the model never loaded; the DLL import failed with Win32 error 126 ("module not found") and nothing said which file was missing. On the development machine the same bundle loaded without any sign of trouble.
- **Cause:** `ggml-cpu.dll` of the 1.9.1 bundle imported `libgomp-1.dll`, GCC's OpenMP runtime, which the MinGW build linked in but the bundle's catalog did not ship. On the development machine the Windows loader found that DLL through PATH, in the Scoop MinGW install, so the gap stayed invisible. Established by reading the import table of the installed bundle with the new PE reader, which names exactly that import. The tester's own error text was not retained; that it was error 126 is inferred from the import gap, not observed.
- **Violated invariant:** Every DLL of the native bundle resolves its imports from the bundle itself or from Windows; the machine that built it must not be able to hide a missing dependency.
- **Recurrence cue:** A catalog change, a toolchain change or a new ggml backend that adds an import nobody listed, or a load check run with the default DLL search order, where PATH can answer for a file the bundle lacks. A second, quieter form of the same fault: the old build had `GGML_NATIVE=ON`, so the CPU code was tuned to the build machine's processor; the dynamic CPU variants of the MSVC build remove it, and a return to a single `ggml-cpu.dll` would bring it back.
- **Regression coverage:** `NativeRuntimeLoaderTests.ADllImportingARuntimeTheBundleDoesNotShipIsNamedWithItsImport` reproduces the failure with the search order limited to the native folder and System32, and pins the message that names the DLL and the import. On the script side `scripts/tests/lib/pe-imports.tests.ps1` and `scripts/tests/commands/publish-native-runtime.tests.ps1` pin that publication refuses a bundle with such an import.

## A backend's name was asked of the wrong ggml DLL

- **Trigger:** First model load on the MSVC bundle with dynamic backends (candidate 1.9.2), run through the opt-in system test `WhisperReferenceAudioSystemTests` on an isolated data root, before the bundle was published.
- **Observed symptom:** `EntryPointNotFoundException: Unable to find an entry point named 'ggml_backend_reg_name' in DLL 'ggml'`, thrown from `NativeRuntimeLoader.EnsureBackendsLoaded` right after the backends had loaded. Every unit test was green: none of them reaches a real ggml.
- **Cause:** The backend registry is split between the two ggml DLLs. `ggml.dll` loads and lists the backends (`ggml_backend_load_all_from_path`, `ggml_backend_reg_count`, `ggml_backend_reg_get`, `ggml_backend_dev_count`); `ggml-base.dll` owns each entry (`ggml_backend_reg_name`, `ggml_backend_reg_dev_count`). The P/Invoke declared the name lookup on `ggml`. Established by listing both DLLs' exports with `dumpbin /EXPORTS`.
- **Violated invariant:** Every `[DllImport]` of `WhisperPInvoke` names the DLL that actually exports the function.
- **Recurrence cue:** A new ggml P/Invoke written from the header's module name rather than from the DLL's export table, or a whisper.cpp upgrade that moves a function between `ggml.dll` and `ggml-base.dll`. The symptom is late, at the first model load, never at build or unit-test time.
- **Regression coverage:** None in the unit suites: proving the export needs the real DLLs. The opt-in system test `WhisperReferenceAudioSystemTests.InstalledWhisperTranscribesTheReferenceSpeech` exercises every registry P/Invoke against the installed bundle and is the check to run before a native bundle is published.

## The catalog changed and nothing provisioned it again

- **Trigger:** Deckle 0.72.0, whose catalog names bundle 1.9.2 (`whisper.dll`, the MSVC runtime, dynamic ggml backends), started on a machine whose native folder still held bundle 1.9.1 (`libwhisper.dll` and the MinGW runtime), without an update continuation provisioning it first: a developer build, a cancelled continuation, a folder filled by hand.
- **Observed symptom:** Transcription stayed off with no window and no download. The hotkey answered "Dictation isn't set up yet / Open Settings › Dictation to download the speech engine and model.", a page renamed Transcription, in a body too long for the HUD card, so its end was cut. On the maintainer's machine, after 1.9.2 had been provisioned, the native folder still held five 1.9.1 files beside the new catalog (`ggml-cpu.dll`, `libgcc_s_seh-1.dll`, `libstdc++-6.dll`, `libwhisper.dll`, `libwinpthread-1.dll`), read with `clean-native.ps1 -WhatIf`.
- **Cause:** Three gaps, each established in the code. Startup only skipped the engine and opened a tray incident when the runtime was missing; nothing offered the download. `NativeRuntime.IsInstalled` checked file presence alone, so a catalog present but not loading here counted as installed and the install plan skipped it. Extraction and folder import wrote the catalog's files and removed none, so an older bundle's DLLs stayed, and `ggml_backend_load_all_from_path` scans that folder for `ggml-*.dll`. That a stale `ggml-cpu.dll` beside the 1.9.2 variants is actually loaded is an interpretation from ggml's search rules, not observed. The HUD strings were literals that named a page by hand.
- **Violated invariant:** A native folder holds exactly the catalog of the running build, and "installed" means the catalog loads on this machine; when it does not, the person is told why and offered the download, never left with a silent skip.
- **Recurrence cue:** Any change to `NativeRuntime.RequiredDllNames` or `CurrentBundle`, a renamed Settings page named in a message, or a new HUD string written as a literal or longer than the card's one body line.
- **Regression coverage:** `NativeRuntimeTests.InstallingFromTheBundleLeavesTheCatalogAlone` and `CopyingFromAFolderLeavesTheCatalogAlone` seed the 1.9.1 files and pin that both provisioning paths remove them. `Deckle.Hud.Tests.HudMessageFitTests` measures every HUD resource string against the card's text column. The startup offer (`App.SpeechRepair.cs`) has no automated test: it opens a WinUI window, and the App suite creates none. What proves it is a launch on a data root whose native folder holds 1.9.1 alone, run by the maintainer.

## The startup load check made every start abort

- **Trigger:** Deckle 0.72.2 Release started with transcription present and the 1.9.2 runtime installed. Version 0.72.0 started on the same folder; the load check at startup arrived in 0.72.1.
- **Observed symptom:** Four crashes in a row right after "Starting transcription", exit code `0xC0000409` faulting in `ucrtbase.dll`, until the supervisor gave up its relaunch budget. The load check had just logged that it passed; no crash dump was written, since a fail-fast bypasses the capture.
- **Cause:** `NativeRuntimeLoader.Check` loaded the catalog and freed it. `ggml-base.dll`'s static initializer (`ggml.cpp:22`) sets ggml's `std::terminate` handler and asserts the previous one is not its own; the free left that handler set, the reload at the same address found it and aborted. Established outside Deckle with a script replaying the check's load and free order, which prints `GGML_ASSERT(prev != ggml_uncaught_exception) failed`, and passes once `ggml-base.dll` stays loaded. A first diagnosis blamed five stale 1.9.1 DLLs in the native folder; removing them changed nothing.
- **Violated invariant:** A DLL whose static initialization asserts it runs once in the process is never unloaded.
- **Recurrence cue:** Any code that frees a whisper.cpp or ggml DLL, or a whisper.cpp upgrade that adds process-wide state to another DLL's initializer.
- **Regression coverage:** None in the unit suites: proving it needs the real DLLs. The opt-in system test `WhisperReferenceAudioSystemTests.InstalledWhisperTranscribesTheReferenceSpeech` now runs the check before the model load in one process, as startup does, and is the check to run before shipping a change to the loader or a new bundle.
