# Tray icon bug notes

## Tray icon gone after an Explorer restart

- **Trigger:** explorer.exe restarts while Deckle runs. Observed on 2026-10-14: Deckle started at 22:50:32, explorer.exe restarted at 22:56:13 (Windhawk restarted at 23:00:14), and the icon was gone afterwards. Louis loses the icon "regularly"; every Explorer restart, whatever its cause, is a trigger.
- **Observed symptom:** The notification area shows no Deckle icon. The process runs, the hotkeys still work, but the menus have no icon to open from. The journals hold nothing for it: no code observed the restart.
- **Cause:** Established from the code, not yet confirmed on screen. The shell rebuilds the notification area from an empty table when the taskbar is recreated, and tells every top-level window so through the `TaskbarCreated` broadcast. `TrayIconManager` added its icon once, in `Register`, and nothing re-sent it. It could not have reacted either: the icon's owner window was `MessageOnlyHost`, an `HWND_MESSAGE` window, and a message-only window never receives a broadcast (Microsoft Learn, Window Features: message-only windows). The sibling `TaskbarCoverHost` already handled `TaskbarCreated` on a hidden top-level window of its own.
- **Resolution (2026-10-14):** the icon's owner is a hidden top-level window `TrayIconManager` creates itself (`WS_POPUP`, never shown, `WS_EX_TOOLWINDOW`), whose `WndProc` receives `TaskbarCreated` and the tray callback. `TrayIconRegistration` keeps the last icon and tip and sends the whole entry again with `NIM_ADD`; a refused add (the shell's tray window still coming up) is retried every 500 ms through a window timer, five attempts at most, then logged as a Warning. The hotkeys and the cursor signal stay on `MessageOnlyHost`. Seen running on 2026-10-14 at 23:47 through a console harness that drives `TrayIconManager` on a plain Win32 pump: explorer.exe killed at 23:47:19, the icon absent at 23:47:20, `TaskbarCreated` received at 23:47:21.4, the icon added again at the first attempt and present on every probe after. Not yet seen in Deckle itself, whose resident build was from `main` at that time.
- **Side fix:** the initial status the App set before `Register` ("Dictation not set up" when speech is not provisioned) went to a `NIM_MODIFY` on a window that held no entry and was lost; `Register` hard-coded "Ready". The registration now keeps a status set before the add and the add carries it.
- **Violated invariant:** The icon is in the notification area as long as the process runs, whatever the shell does in between.
- **Recurrence cue:** a tray icon owned by a message-only window or any window that receives no broadcast; a `Shell_NotifyIcon(NIM_ADD)` that runs once with no `TaskbarCreated` handler beside it; a journal that holds no `Deckle-Shell` line at all for an Explorer restart (the Informational "Taskbar recreated, tray icon added again" is the sign the handler ran).
- **Regression coverage:** `TrayIconRegistrationTests.ATaskbarRecreationAddsTheIconBackWithItsLastStatus` (regression) pins the re-add: a full `NIM_ADD` with the callback message and the status of the moment, through the `INotifyIconApi` seam. `ARefusedReaddIsRetriedThenGivenUp` pins the retry decision. The broadcast reaching the hidden window, and the Win32 call itself, are not driven by a test: the manual check is the icon coming back a few seconds after an Explorer restart, with the Informational line in the journal, as the harness run above showed.
