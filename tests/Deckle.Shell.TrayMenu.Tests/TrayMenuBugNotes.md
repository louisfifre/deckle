# Tray menu bug notes

## Quick-actions panel shows nothing on left click

- **Trigger:** A left click on the tray icon, on v0.39.0, the panel's first release (built and merged without a run on screen). Louis, 2026-10-12: "au clic gauche, il se passe rien".
- **Observed symptom:** No panel appears. The diagnostics logs of his 2026-10-12 session (11:53 to 14:05) hold no `Deckle-TrayMenu` event at all: the provider is Verbose and gated by the Windowing activity, off, so neither the prime cycle nor a `Show()` left a trace.
  Seen again on v0.40.0, the build that carries the fix below (Louis, 2026-10-12, 15:19 to 15:30, session `2026-10-12-72ce`): "au clic gauche, il ne se passe toujours rien". That session's journal holds neither `PanelDismissedWhileOpening` nor `PanelSizeRejected`, while the menu's `PresenterSizeRejected` warning is there (15:21:00), so non-gated warnings do reach the journal. The Windowing activity was still off.
- **Cause:** Not established. The v0.40.0 run weakens both hypotheses below: a dismiss during `Show()` would now have logged the first warning, a rejected size the second. What remains: `Show()` never runs (the click does not reach the host, or the handler stops before the flyout), or `Show()` completes with a flyout WinUI considers open and nothing on screen (carrier not shown, off screen, or zero sized). The next run needs non-gated milestones at click reception and at the end of `Show()` (carrier size and position, `IsOpen`), or the Windowing activity on. The panel's open path differs from the context menu's, which works, in two places, ranked:
  1. `FlyoutShowMode.Standard`: the panel takes keyboard focus, the menu (`Transient`) does not. A WinUI flyout renders in a popup window the carrier owns; if moving focus into it activates that popup, Windows deactivates the carrier toward its own popup, and `OnCarrierDeactivated` hid the panel before `Show()` returned. Not confirmed on screen nor in documentation; fits "nothing happens" exactly.
  2. The presenter capture kept any positive `FlyoutPresenter.DesiredSize` from the prime cycle, the `> 0` check the menu note below describes. A degenerate capture would open a card at the presenter's minimum size rather than nothing; a weaker fit.
- **Violated invariant:** A click on the tray icon opens its surface, and the surface closes only on a dismiss the user caused.
- **Recurrence cue:** a flyout opened in `Standard` mode on a carrier that hides on `Deactivated`; a new tray surface whose carrier size comes from a captured presenter without a check against what it holds; a session whose journal shows no non-gated line for a silent open (the `PanelDismissedWhileOpening` and `PanelSizeRejected` warnings now cover both).
- **Regression coverage:** `TrayWindowOwnershipTests.ADeactivationTowardTheCarriersOwnPopupIsNotADismiss` drives `TrayWindowOwnership.IsOwnedBy`, the rule the carrier applies before raising `Deactivated`; `TrayMenuSizingTests.APresenterSmallerThanThePanelContentIsNotTrusted` drives the check the panel's capture applies. Whether a `Standard` flyout activates its popup stays a manual check: the `ActivationMovedToOwnedPopup` Verbose event (Windowing activity on) says so when it happens.

## Context menu opens one item tall and scrolls

- **Trigger:** Unknown precisely. Louis reported the right-click tray menu opening one line tall, scrollable, over several months: a few times, then on every open for a while, recently once and briefly. "Every open" fits a bad size kept until the process restarts.
- **Observed symptom:** The menu card is one item tall (about 32 DIP) and its items scroll inside it. His diagnostics logs hold no bad open: the `Deckle-TrayMenu` provider is Verbose and gated by the Windowing activity, and the only recorded menu session (2026-07-16, `app.jsonl.0001`) shows good opens, items 32 DIP and separators 3 DIP, carrier 179.5 x 268 DIP. That session also shows `Frame.Loaded`, and so the prime cycle, running about 150 ms after the host is built, before any open.
  Seen again on v0.40.0, which carries the size check below (Louis, 2026-10-12, session `2026-10-12-72ce`): the first right click after launch opened one line tall; a click elsewhere and a second right click opened it right. The journal holds one `PresenterSizeRejected` warning (15:21:00) and no way to tell which open it belongs to, the other menu events being gated. Either reading says the carrier size check alone did not prevent the one-line open at launch: if the warning belongs to the first open, the carrier was sized from the items and the card still showed one line; if it belongs to the second, the first open's capture passed the check and still showed one line. Next thing to read: what the `MenuFlyoutPresenter` itself measures and shows at the first open, apart from the carrier (items not yet realized is one candidate), with the Windowing activity on.
- **Cause:** Established in code for the carrier's part, not yet for the whole (see the v0.40.0 run above): under `FlyoutPlacementMode.Full` the visible card is the carrier window's size; the carrier took the presenter size captured once at the prime cycle with only a `> 0` check, and nothing re-captured it. `MenuFlyoutPresenter` has `MinHeight = MenuFlyoutThemeMinHeight` (32 DIP, generic.xaml), so a degenerate measure reports exactly one item's height, which passes that check. Which event produced the degenerate capture is a hypothesis, ranked:
  1. The prime captured a clipped presenter `DesiredSize` (the prime opens with the default placement on the hidden carrier, wherever it sits; the available height there is not controlled), and it stuck for the process lifetime. Fits "then every time".
  2. The prime ran before the items were laid out, or not at all before an early right click, so the detached-measure fallback ran with near-zero item heights and the carrier was only the 8 DIP margin; the presenter then showed at its MinHeight. Fits a single brief occurrence.
  3. The prime callback hid a menu the user had just opened (no visibility guard). Less likely for the first click, since the prime runs before any open in the logged session; it would close the menu rather than shrink it.
- **Violated invariant:** The carrier window is never sized below the items it shows.
- **Recurrence cue:** Any one-shot measurement cached for the process lifetime without a sanity check against what it must hold, or without a refresh; any positivity check standing in for a size check on a control that has a MinHeight; a new tray surface (the quick-actions panel shares the pattern) that sizes its carrier from a captured presenter without the same check.
- **Regression coverage:** `TrayMenuSizingTests.CapturedSizeSmallerThanItsItemsIsNeverUsed` drives `TrayMenuSizing.Decide`, the decision the host uses. The capture itself (WinUI layout inside the popup) has no natural seam and stays unverified until seen on screen; a rejected capture now raises the `PresenterSizeRejected` warning, which is logged whatever the Windowing verbosity.
