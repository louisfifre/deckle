# Explorer re-injection bug notes

## A second engine in one explorer made it fail fast in Windows.UI.Xaml.dll

- **Trigger:** The taskbar engine started in an explorer that already had XAML Diagnostics initialized by an earlier copy of the DLL. Two routes, both observed. A Deckle restart (from the tray, or after Deckle was killed) re-injected the engine into the explorer whose previous engine had just unloaded: 2026-11-10 17:58:18, 2026-11-11 01:12:41 and 01:52:28. The development console (`Deckle.Shell.Taskbar.Harness`, given its own pipe in 0.104.0 so it could inject "while the app keeps its engine in explorer") injected a second copy beside the app's live engine: 2026-11-10 16:07:49 and 16:42:20.
- **Observed symptom:** Explorer died with event 1000, faulting module `Windows.UI.Xaml.dll` 10.0.26100.9711, exception `0xc000027b` (stowed exception), fault offset `0x667f`, five times. In the three restart cases it died within 300 ms of the new engine's `tap_site_set`, during `AdviseVisualTreeChange`: no `advised` record, and at 01:12 not a single element reached the engine. The tray icon and the hotkeys were lost with it (the startup's resilience is a separate workstream). The console sessions' transcripts show the harness starting (`source ...` at 16:07:49.023) and its engine meeting a XAML thread (16:42:20.030), 220 to 470 ms before the two console crashes.
- **Cause:** Established as a correlation, interpreted as a mechanism. Across the logs of 2026-11-09 to 11, every `0x667f` crash hit an explorer that hosted the engine for the second time (5 of 5), and no first injection into a fresh explorer ever produced it (about 16). Re-hosting did not always crash: 7 of 12 survived. Before 0.104.0 none of 5 re-hosts crashed, and from 0.104.0 on 5 of 7 did. No native change between those builds touches XAML, and the console's own pipe arrived in 0.104.0, so that part is uncertain. The mechanism is read from microsoft-ui-xaml, which shares this code with system XAML but is not the same binary, so it is inferred. `DiagnosticsInterop` is a process-wide singleton that holds a raw pointer to the current `XamlDiagnostics` (`DiagnosticsInterop.cpp`, `Launch`). The `XamlDiagnostics` destructor releases that singleton and the runtime object cache and turns the diagnostics feature flag off for the whole process (`XamlDiagnostics.cpp`, the destructor). Each `InitializeXamlDiagnosticsEx` creates a new `XamlDiagnostics` (`DebugTool.cpp`). An engine that unloads, or a second one that comes and goes beside the first, therefore destroys or replaces state the other diagnostics still use. Windhawk's taskbar styler documents the same ordering hazard. The stowed exception's HRESULT was not read: the WER reports need elevation, and no dump was taken.
- **Violated invariant:** XAML Diagnostics are initialized at most once per process, and the TAP that holds them never leaves it. The rule lives in `native/Deckle.Shell.Taskbar.Native/residency.h`. The DLL that first claims an explorer parks there for the life of the process instead of unloading. A later copy hands the parked engine its pipe, or is refused when that engine serves another Deckle. `ConnectToXamlDiagnostics` refuses a second call (`xamldiag/tap_connection.cpp`).
- **Recurrence cue:** Any code that unloads the DLL after `InitializeXamlDiagnosticsEx` answered, releases the last reference to the IXamlDiagnostics site, unadvises and re-advises to "start over", or calls `InitializeXamlDiagnosticsEx` again (Windhawk's settings-change path does exactly that). Also a second injection route, a tool that loads its own TAP copy into a target the app serves, or a claim name that stops covering every copy in the process. Watch for a native update that "doesn't take": the resident build keeps running until explorer restarts, and the cure is that restart, never an unload.
- **Regression coverage:** `EngineResidencyTests.ASecondCopyInAProcessWhoseEngineIsServingLeavesWithoutStartingAnEngine` starts two copies in the test process through the exported hook procedure. It checks that the second leaves without starting an engine. It fails on the pre-fix DLL, whose second copy starts a full engine. Parking and the hand-over to a later copy need a process with a XAML core whose diagnostics answer, which no test process has. `TaskbarEngineHostStopTests` pins that the host counts `parked` as a confirmed stop. The proof of the restart route is a live run: Deckle restarted from the tray, then started again, with the same explorer alive and the engine reconnecting through `tap_kept`.

The `dcomp.dll` `0xc0000602` crashes of the same days are a separate family, linked to the engine but not to re-injection: see `ExplorerCompositionDiagBugNotes.md`.
