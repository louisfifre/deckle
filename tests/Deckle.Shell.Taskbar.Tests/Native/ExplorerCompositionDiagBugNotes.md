# Explorer composition diagnostics bug notes

## The XAML composition diagnostics made explorer fail fast in dcomp.dll

- **Trigger:** Any explorer that hosted the taskbar engine, from its first injection on. The crashes came every few minutes during heavy use, typically when the taskbar's XAML rebuilt many elements at once (a fullscreen window leaving or entering, focus returning to the taskbar). On 2026-11-12 at 02:47:14 the engine received about 320 visual tree changes on one XAML thread, `Windows.UI.Composition.Visual` and `SpriteVisual` among them, and explorer died at 02:47:17.
- **Observed symptom:** Explorer died with event 1000, faulting module `dcomp.dll` 10.0.26100.9549, exception `0xc0000602` (fail fast), fault offset `0xb814`, every time. There were 43 such crashes from 2026-11-09 to 2026-11-12 (5, 16, then 19 in one night) and none in the 30 days before. Windows restarted explorer each time, so the taskbar and the desktop vanished and came back. The LiveKernelEvent 141 and BlueScreen records that WER logs at the same instants are old reports re-sent (their WER folders date from April to September 2026), not GPU resets.
- **Cause:** Established as a correlation, interpreted as a mechanism. 48 of the 49 explorer crashes from 2026-11-09 on hit an explorer into which the app had injected the engine. The remaining one (2026-11-09 00:35) fell while the engine was being developed, before the app started it, and is unexplained. The mechanism comes from Windhawk's windows-11-taskbar-styler source and was not observed here. With XAML Diagnostics on, Windows.UI.Xaml.dll also creates composition diagnostics. They rebuild a process-wide visual tree walker without any locking each time a DirectComposition visual is added, so two UI threads adding visuals at once corrupt the heap. Explorer runs several XAML threads (six distinct thread ids in one night's trace). No crash dump or stack was read: the WER reports need elevation.
- **Violated invariant:** The composition diagnostics are never created in a process the engine serves. Windows.UI.Xaml.dll reads `HKLM\Software\Microsoft\XAML\Debug\DisableCompositionDiag` once, inside the first `AdviseVisualTreeChange`, and the engine answers 1 to that read through Windows.UI.Xaml.dll's own registry imports. See `native/Deckle.Shell.Taskbar.Native/xamldiag/composition_diag_guard.h` and the call in `VisualTreeWatcher::Advise`.
- **Recurrence cue:** A `dcomp.dll` `0xc0000602` crash of explorer again. A `composition_diag_active` warning from the engine: the value was read before the guard, or the guard could not be installed. A `Windows.UI.Composition.*` type in the engine's `visual_add` records, which the guard keeps out. Any change that calls `AdviseVisualTreeChange` outside the guard's scope, moves the call to another thread than the one inside the scope, or unpins the DLL once the guard is installed. An explorer that already read the value before an engine with the guard arrived keeps the diagnostics on until it restarts.
- **Regression coverage:** `CompositionDiagGuardTests.TheAdvisingThreadReadsTheCompositionDiagnosticsAsDisabled` reads the value the way Windows.UI.Xaml.dll does, through its own import slots, loaded in the test process, and expects 1. `EveryOtherReadSeesTheRegistryAsItIs` checks that the redirection changes nothing outside the scope. They prove the answer, not that explorer then skips the diagnostics: that part is checked live, in a fresh explorer, by the `composition_diag_disabled` record and by the absence of composition types in `visual_add`.
